# Implementing the ledger on Turso (VCL)

For [vibecodelisboa#506](https://github.com/scrollinondubs/vibecodelisboa/issues/506).
The self-hosted plugin stores founder state in Postgres through
`founder_ledger`. The VCL student dashboard stores it in Turso, with the same
schema and the same interface, written in TypeScript with drizzle. VCL is the
canonical store for student data. Nothing is replicated to a self-hosted
install, except through the founder bundle export when a student chooses to
move.

## What VCL takes from here, and what it writes itself

| Piece | Source of truth | VCL's copy |
|---|---|---|
| Table and column names, types, constraints | `schema/migrations/*.sql` | A drizzle `sqliteTable` per table in VCL's schema, generated by drizzle-kit into a normal VCL migration |
| Method names, arguments, return shapes, errors | `founder_ledger/interface.py` | A TypeScript `Ledger` interface with the same methods, in camelCase |
| Behaviour | `tests/ledger_conformance.py` | A port of those cases to VCL's test runner (jest), run against a local libSQL file |

The SQL files are the contract. If the drizzle tables drift from them, a founder
bundle exported from VCL will not import into a self-hosted install.

## Steps

1. **Tables.** Transcribe each `CREATE TABLE` in `001_ledger.sql` into
   `drizzle/schema.ts` with `sqliteTable`. Types map directly: `TEXT` to
   `text()`, `INTEGER` to `integer()`, `DOUBLE PRECISION` to `real()`. Keep the
   `CHECK` constraints: drizzle supports them in the table's extra-config
   callback with `check()`, and they carry the gate rules (see
   `schema/README.md`), so they must not be dropped. Keep `ON DELETE CASCADE` on
   every `founder_id` reference.
2. **Migration.** Run `npm run db:generate`, then diff the generated SQL against
   `001_ledger.sql`. They should differ only in quoting and statement order. Any
   other difference is drift, so fix `schema.ts` rather than the plugin.
3. **Adapter.** Implement the interface over drizzle queries. Things that have
   to match the Python implementation exactly:
   - ids are `crypto.randomUUID()` strings, and timestamps are
     `new Date().toISOString()` (same ISO-8601 UTC shape)
   - JSON columns are `JSON.stringify`'d on write and parsed on read.
     `earlyvangelist` and `sean_signoff` are 0/1 in the table and booleans in
     the API.
   - every query filters on `founder_id`, including lookups by row id
   - `recordGateDecision` validates the evidence refs against the same
     founder's rows, checks the stage 3 sign-off rule, and moves
     `current_stage`, all inside one `db.transaction()`
   - artifact versions count per `(founder_id, kind)` from 1, and PR/FAQ
     versions per founder from 0
4. **Conformance.** Port `tests/ledger_conformance.py` case for case. The raw
   `CHECK`-constraint cases (`test_schema_rejects_*`) matter most. They prove
   the rules hold even when the adapter is bypassed.
5. **Founder bundle.** The student dashboard's export writes the format in
   [`bundle-format.md`](bundle-format.md) with `source: "vcl"`. Read with the
   `list*` methods and follow the spec's JSON encoding and sort order exactly:
   the self-hosted import checks every file's sha256, and the round-trip test
   compares bytes. Implement `importFounderRows` too, so a founder can move back.
   To check the exporter, import its bundle with `founder-os import` into a
   SQLite ledger, export again, and diff the two directories. Only
   `exported_at` may differ.
6. **Progress webhook receiver.** The instructor dashboard receives the opt-in
   webhook from self-hosted graduates. Issue each student their own URL and
   signing secret, and verify every request as the spec describes, rejecting
   timestamps more than 300 seconds old.
7. **Tenancy.** A VCL request resolves the student's `founder_id` from their
   session and passes it on every call. `export_corrected_labels` is the only
   cross-founder call. Keep it behind an instructor or admin check, never
   reachable from a student session.

## Why not run the Python adapter against Turso?

It would work. libSQL speaks SQLite, and `founder_ledger/sqlite_adapter.py` is a
few lines away from a libSQL client. But VCL's application code is TypeScript,
its migrations go through drizzle-kit, and the coach runs on the Cloudflare
executor. A Python service in the middle would be one more thing to host. The
SQLite adapter's job here is to be the reference: the conformance suite passes
on it, so it is a working example of every rule.

## Separate database or shared?

VCL's current drizzle schema has no table named like any ledger table. Two
options:

- **Tables in VCL's existing Turso database.** Simplest joins to `users` and
  cohorts, one migration pipeline. The cost is that generic names like
  `artifacts` and `labels` become reserved in VCL's namespace.
- **A separate Turso database for the ledger.** Clean namespace, and a founder
  export is a filtered dump of one database. The cost is a second connection and
  no cross-database joins.

This is an open question for Sean on #506.
